# Restart interview — 17 September 2026

Status: accepted direction. This is a faithful decision summary, not a verbatim
transcript. Quotations below preserve specific user wording; other text summarizes
the discussion. Later clarifications take precedence over earlier proposals.

## Intent

Start over with a constructive mathematics repository in the form of a beautiful,
static, interactive online book. Readers see and run code demonstrating examples
and proofs. Build from foundations through arithmetic, algebra, abstract algebra,
and eventually mathematics needed for physics. Explicit state, memory, and steps
belong in the foundations. No silently available infinite work or objects.

Use [Harness engineering](https://openai.com/index/harness-engineering/) to make
the repository navigable, observable, and mechanically verifiable for agents.

## Q1 — Why restart

The existing visual style, layout, computer visualization, use of the computer,
and supporting hardware material are not the desired approach. Remove them and
build slowly enough to establish each concept carefully. Success means a good
structure for both content and source, plus the right explanatory approach and
writing style. Do not let the previous implementation constrain the new book.

## Q2 — Readers and first substantial outcome

Anyone interested in mathematics and science, including engineers and
mathematicians. The content itself should provide access to the prerequisites.
After the first substantial chapter or part, readers should understand and code
foundational constructions and proofs, including addition and its properties.
This is the destination of the first part, not a demand to fit it all into the
first review chapter.

## Q3–Q4 — Finite construction and state

A program attempts a construction within finite steps and bounded memory.
Explicitly constructed finite collections are permitted. The objection is to
something magically containing infinitely many things without constructing them.
Computation and its steps are the intended notion of state, and state can affect
membership and claims.

The user wants to investigate deeper concepts, including Gödel's incompleteness
theorems, in the eventual system. No theorem about incompleteness has been changed,
proved, or refuted by this interview.

## Q5 — Proofs

Develop a mathematically defensible proof concept and a small proof engine,
described by the user as “lean light light light”. Aim for formally rigorous
proofs within the chosen constraints. The exact calculus is work to do, not a
settled deliverable from the interview.

## Q6 — Static delivery

Everything executes in the reader's browser when visiting the book URL. No
backend is required. The earlier suggestion that double-clicking a downloaded
HTML file must work was not adopted; ordinary static hosting is sufficient.

## Q7 — Prose and code

Both are central. Show executable code, but do not provide a reader code editor.
Keep the interface simple. Focus on content and structure before advanced layouts.
The desired visual character remains a beautifully typeset early-20th-century book.

## Q8 — Barber and changing membership

The user's clarification: construct a queue of people who have not yet shaved
themselves. Before his first self-shave the barber qualifies. After he shaves
himself he no longer qualifies and should be removed. This is about performed
actions, not intentions.

Record that as a stateful eligibility/update example. The assistant distinguished
this changing-state specification from the classical time-independent barber
condition. The project will make states, evidence, and update rules explicit
rather than claim that finite construction alone resolves every self-reference
problem. Do not replace the user's operational example with a discussion of intent.

## Q9 — Proofs that predict behavior

An initial abstract question about reusable proofs was unclear. The discussion
moved to copying rows of marks. The user emphasized the missing substrate:
dedicated or allocated memory for source and destination, an instruction model,
and the ability to reason about different configurations.

The accepted goal is a generalizable proof showing that a construction can be
performed under stated memory and step constraints without executing every
variation. The user wrote:

> A generalizable proof then should ideally show that given no bugs and up until
> a certain set of resource constraints in terms of steps and memory we expect
> something to be able to be performed without actually performing all variations
> of that action

The design separates mathematical correctness under model assumptions from bugs
in the implementation. No particular induction principle was selected. Any rule
for reasoning about repeated computation must be stated and justified.

## Q10 — Navigation

Parts, chapters, sections, separate concept pages, and a good organizing index.
Provide a main ordered reading path with optional supporting material. Abandon
the previous single continuous page.

## Q11 — Writing references

The user dislikes formal language for its own sake and empty fancy words. They
like programming and named a broad range of influences, recorded in
[Writing and visual influences](../references/influences.md). The earlier proposed
row-of-marks opening was illustrative, not an approved final chapter opening.

## Q12 — Trusted starting point

Accept explicit primitive syntax, inference rules, and a small trust boundary.
Use finite derivations and bounded checking. Distinguish accepted evidence,
invalid evidence, and unfinished checks. Explain and review the rules
mathematically and test the implementation. Do not require the initial system to
justify all of its own rules internally.

## Q13 — Where to begin

Begin in the spirit of the Peano axioms article or a good foundations book.
Introduce the chosen computer model and how programs run on it. The user leaves
room for a register machine, C/Wasm, TypeScript with explicit costs, or another
pedagogically sound substrate. No implementation language was mandated.

## Q14 — What a step means

A simplified computer is acceptable. A step can mean a clock cycle or a program
execution step, provided it does not conceal infinite work. Choose what best
serves the book and mathematical foundations. The accepted design direction is
a small deterministic machine with finite memory and bounded elementary work;
its exact specification remains open.

## Q15 — First review milestone

Accept the smaller complete slice: organization plus one carefully developed
opening chapter, supporting concept pages, working code, and a minimal checked
claim. Provide a route toward addition, but review the first slice before writing
the remaining chapters.

## Q16 — Exhaustion clarification

The user rejected making resumability or rollback a foundational concern:

> from a proof point of view it's just a non completed computation.

They mentioned `FALSE`, `None`, or `oom` as possible operational outcomes. A saved
state can be useful for debugging. The accepted distinction is non-completion
under the given constraints, not a completed result. An operational false/error
flag must not be presented as a logical proof of negation. No initial resume or
transactional semantics are required.

During implementation the user clarified:

> exhaustion and non-completed is the same as failure or negative result

Use that terminology: resource exhaustion/non-completion is a failed computation
and a negative result under the given constraints. This operational negative
result does not by itself prove the negation of the proposition being checked.
